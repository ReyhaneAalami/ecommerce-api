# گزارش تست بار و ارزیابی عملکرد API فروشگاهی

**پروژه:** Ecommerce API  
**ابزار:** Locust 2.47.0  
**فریم‌ورک:** FastAPI  
**پایگاه داده:** PostgreSQL 16.4  
**نسخه Python:** 3.11.9

> وضعیت گزارش: گزارش اولیه. نتایج تست دیتابیس مستقل و داده‌های ماک هنوز باید تکمیل شوند. هیچ عددی برای مراحل اجرا نشده در این گزارش فرض یا ساخته نشده است.

## ۱. هدف

هدف، سنجش زمان پاسخ، نرخ پردازش درخواست، نرخ خطا و مصرف منابع سامانه در بارهای مختلف و با حجم داده متفاوت است. همچنین هدف شناسایی Endpointها و منابعی است که با افزایش بار به گلوگاه تبدیل می‌شوند.

## ۳. مفاهیم و معیارها

- **Average:** میانگین زمان پاسخ؛ ممکن است تحت تأثیر چند درخواست بسیار کند قرار گیرد.
- **P50:** صدک ۵۰؛ نیمی از درخواست‌ها در این زمان یا سریع‌تر پاسخ گرفته‌اند.
- **P95:** صدک ۹۵؛ ۹۵ درصد درخواست‌ها در این زمان یا سریع‌تر پاسخ گرفته‌اند.
- **P99:** صدک ۹۹؛ برای مشاهده تأخیرهای انتهایی و تجربه بدترین بخش کاربران مفید است.
- **RPS:** تعداد درخواست‌های پردازش‌شده در هر ثانیه.
- **Concurrency:** تعداد کاربران مجازی فعال در یک بازه زمانی؛ با کاربران روزانه یکسان نیست.
- **Error Rate:** نسبت درخواست‌های ناموفق به کل درخواست‌ها.
- **4xx:** خطاهای مربوط به درخواست، ورودی یا مجوز.
- **5xx:** خطاهای سمت سرور.
- **Timeout:** درخواست‌هایی که در مهلت تعیین‌شده پاسخ نمی‌گیرند.

## ۵. تحلیل اولیه

در این اجرای محدود خطای ثبت‌شده‌ای مشاهده نشد. P50 و P95 پایین بودند، اما P99 و Maximum بسیار بالاتر بودند. بنابراین میانگین به‌تنهایی تصویر مناسبی از تجربه همه درخواست‌ها ارائه نمی‌کند.

در تست اولیه حتی Endpoint سلامت نیز تأخیرهای انتهایی مشابه داشت. بنابراین در این مرحله نمی‌توان کندی را به Query خاص محصولات نسبت داد. علت می‌تواند به زمان‌بندی سیستم‌عامل، رقابت منابع روی لپ‌تاپ، وقفه پردازش، API یا دیتابیس مربوط باشد و برای تشخیص آن به تکرار کنترل‌شده و پایش منابع نیاز است.

## ۶. محدودیت‌های تست اولیه

1. فقط ۱۰ کاربر همزمان استفاده شده‌اند.
2. مدت تست کوتاه بوده است.
3. تست اولیه با داده‌های موجود آن زمان انجام شده و هنوز مقایسه کنترل‌شده با دیتابیس کاملاً خالی و دیتابیس دارای داده ماک تکمیل نشده است.
4. مولد بار و API روی یک سیستم محلی اجرا شده‌اند.
5. برای نتیجه‌گیری درباره ظرفیت نهایی، باید تست‌های بیشتر و پایش منابع انجام شوند.

## ۸. نتایج تکمیلی

پس از هر اجرا، فایل CSV خروجی Locust و نمودارهای زیر به این گزارش افزوده می‌شوند:

- Response Time و Percentiles
- RPS در طول زمان
- تعداد درخواست‌های موفق و ناموفق
- Error Rate
- مصرف CPU و RAM
- تعداد اتصالات و وضعیت Queryهای PostgreSQL

## ۹. نتیجه‌گیری

نتیجه فعلی فقط نشان می‌دهد که در اجرای اولیه با ۱۰ کاربر مجازی و سناریوی GET-only، ۵۹۲ درخواست بدون خطای ثبت‌شده پاسخ گرفته‌اند؛ با این حال تأخیر P99 غیرعادی است و نیاز به بررسی دارد. تعیین ظرفیت نهایی سامانه یا اعلام آمادگی برای ۱۰۰ هزار کاربر روزانه با این تست محدود امکان‌پذیر نیست.

پس از تکمیل تست‌های دیتابیس خالی و داده‌دار، نتایج در این بخش مقایسه و گلوگاه‌ها همراه با پیشنهادهای بهبود مستند خواهند شد.
