# تست بار و بررسی عملکرد API فروشگاهی

این پوشه ابزار و مستندات تست بار API مبتنی بر FastAPI را با Locust نگهداری می‌کند.

## وضعیت فعلی و صداقت گزارش

- Locust نسخه 2.47.0 نصب و یک سناریوی اولیه GET-only اجرا شده است.
- اجرای اولیه: ۱۰ کاربر همزمان، حدود ۲ دقیقه، ۵۹۲ درخواست و صفر درخواست ناموفق.
- نتایج اولیه در `reports/REPORT_FINAL_FA.md` ثبت شده‌اند.
- دیتابیس توسعه `ecommerce_db` نباید برای تولید داده آزمایشی حجیم استفاده شود.
- دیتابیس مستقل `ecommerce_loadtest_db` در حال آماده‌سازی است. اجرای Migrationها و تست با داده‌های ماک باید پس از آن انجام شود.
- نتایج هنوز برای نتیجه‌گیری درباره ظرفیت نهایی سامانه کافی نیستند.

## پیش‌نیازها

- Windows / PowerShell
- Python 3.11
- پروژه و محیط مجازی `.venv`
- API در حال اجرا روی آدرس موردنظر
- PostgreSQL تستی مجزا

نصب Locust:

```powershell
.\.venv\Scripts\python.exe -m pip install -r .\requirements-loadtest.txt
```

یا اگر Locust از قبل در محیط پروژه نصب شده است، نیازی به نصب مجدد نیست.

## اجرای رابط گرافیکی Locust

ترمینال اول: API را با تنظیمات دیتابیس تست اجرا کنید. حتماً قبل از اجرا، مقدار `DATABASE_URL` را به دیتابیس تست تغییر دهید و پس از پایان آن را پاک کنید.

ترمینال دوم:

```powershell
.\.venv\Scripts\python.exe -m locust -f .\locustfile.py --host http://127.0.0.1:8000
```

سپس مرورگر را باز کنید:

`http://localhost:8089`

در اجرای اولیه فقط کلاس `PublicShopper` را انتخاب کنید. کلاس‌های مشتری و فروشنده فقط با توکن معتبر فعال شوند.

## اجرای بدون رابط گرافیکی و ذخیره CSV

نمونه اجرای ۱۰ کاربر به مدت ۲ دقیقه:

```powershell
.\.venv\Scripts\python.exe -m locust -f .\locustfile.py `
  --host http://127.0.0.1:8000 `
  --users 10 --spawn-rate 2 --run-time 2m `
  --headless --csv .\reports\baseline
```

برای مراحل بعد، ابتدا ۲۵، سپس ۵۰ و ۱۰۰ کاربر را امتحان کنید. افزایش بار فقط در محیط تست و با نظارت بر CPU، RAM، فضای دیسک و PostgreSQL انجام شود.

## نکات ایمنی

- روی Production تست بار اجرا نکنید.
- فایل `.env`، رمزها، توکن‌ها و اطلاعات کاربران را Commit نکنید.
- سناریوی حاضر فقط درخواست‌های GET دارد و خرید، پرداخت، تسویه یا تغییر موجودی انجام نمی‌دهد.
- قبل از تست Endpointهای احراز هویت، توکن آزمایشی معتبر تهیه کنید.
- از دیتابیس مجزا برای تست استفاده کنید.
- پس از هر مرحله، نتایج CSV، نمودارها و مصرف منابع را ذخیره کنید.

## طرح آزمایش پیشنهادی

| مرحله | حجم داده | کاربران همزمان | مدت پیشنهادی |
|---|---:|---:|---:|
| Baseline خالی | صفر رکورد تجاری | ۱۰ | ۲ دقیقه |
| Smoke | ۱۰۰۰ رکورد مصنوعی | ۱۰ | ۲ دقیقه |
| Load 1 | ۱۰۰٬۰۰۰ رکورد مصنوعی | ۲۵ | ۵ دقیقه |

حجم‌های بزرگ‌تر مثل ۵۰۰ هزار یا یک میلیون رکورد فقط پس از بررسی اندازه واقعی جداول، فضای آزاد دیسک و مصرف RAM اجرا شوند. ۱۰ میلیون رکورد روی لپ‌تاپ فعلی هدف اجباری نیست.

## معیارهای گزارش

- Average، P50، P95 و P99 زمان پاسخ
- Throughput یا RPS
- تعداد کاربران همزمان و نرخ افزایش کاربران
- تعداد درخواست‌ها و Error Rate
- تفکیک خطاهای 4xx، 5xx و Timeout
- CPU و RAM پردازش API و PostgreSQL
- تعداد اتصالات و وضعیت Queryهای دیتابیس
- مقایسه نتایج در حجم‌های مختلف داده

## تفسیر RPS و کاربران روزانه

۱۰۰٬۰۰۰ کاربر روزانه به معنی ۱۰۰٬۰۰۰ کاربر همزمان نیست. برای مثال اگر هر کاربر روزانه ۱۰ درخواست ارسال کند:

`100000 × 10 ÷ 86400 ≈ 11.57 RPS`

این فقط میانگین نظری است. ترافیک واقعی معمولاً در ساعات اوج متمرکز می‌شود؛ ضریب اوج باید بر اساس فرضیه یا داده واقعی مشخص و در گزارش ذکر شود.
